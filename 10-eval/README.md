# 10 — 评估、可观测与成本

> 这是最"不酷"但最决定成败的一层。
> 前面十层都在做功能，这一层回答的是："**我怎么知道我改的这一下是变好了还是变差了？**"
> 没有这一层，你后续所有的优化都是玄学。

## 要搞懂什么

- **评估集（eval set）**：一组"输入 + 期望输出"的样本。**必须自己写**，用模型生成评估集然后让模型去考，是自欺欺人
- **怎么评分**：
  - **确定性评分**：有标准答案的，直接比。能用这个就用这个
  - **LLM 当裁判**：没有标准答案时用模型评分。**但裁判也会错**，得先验证裁判本身
  - **评分细则（rubric）**：把"好"拆成可独立判断的几条标准，比让模型"打个分"可靠得多
- **评什么**：最终答案对不对，**和过程对不对，是两个指标**
  - 一个 Agent 可能答案蒙对了但过程全错，也可能过程全对但最后一步写错了
- **可观测性**：轨迹（trace）记录什么、怎么看。Agent 的失败方式没法靠传统单元测试预测
- **提示词缓存**：前缀匹配，任何一处字节变化都会让后面全部失效。这是成本优化的第一杠杆
- **成本与延迟**：哪些旋钮能调，各自的代价
- **护栏（guardrails）**：输入输出校验、越权拦截、prompt injection 防御
- **human-in-the-loop**：什么操作必须人工确认

## 要写的代码

```
10-eval/
├── tasks/                  # 评估任务集
├── scoring/
│   ├── exact.py            # 确定性评分
│   ├── judge.py            # LLM 裁判
│   └── validate_judge.py   # 验证裁判本身准不准
├── run_eval.py             # 跑批
├── trace_viewer.py         # 轨迹查看
├── cost_report.py          # 成本分析
└── reports/                # 结果存这
```

**`tasks/` — 先建评估集**

拿 `03` 的 Agent（或 `05` 的 RAG）作为被测对象。建 **30 条以上**的样本。

验收：
- [ ] 每条样本包含：输入、期望结果、**判定标准**
- [ ] 样本要覆盖：正常情况、边界情况、**你已知会失败的难例**
- [ ] 至少 5 条是"模型大概率答错"的，留着做回归检测
- [ ] 分成 **train / test 两组**（比如 20 / 10）。**调优只能看 train，test 只在最后看一次** —— 否则你就是在对着答案调参

**`run_eval.py` — 跑批**

验收：
- [ ] 一条命令跑完全部样本，输出每个样本的：通过/失败、耗时、token、成本
- [ ] 汇总：总通过率、平均成本、平均延迟、P95 延迟
- [ ] 结果存进 `reports/`，带时间戳，**能对比两次运行的差异**
- [ ] 能明确告诉你："这次改动，哪几条样本从通过变成了失败"

**`scoring/exact.py` + `judge.py`**

验收：
- [ ] 确定性评分：能精确比的（数字、枚举、JSON 结构）直接比
- [ ] LLM 裁判：用于开放式答案，配合明确的 rubric
- [ ] 裁判的 prompt 里，rubric 必须是**可独立判断的几条**，不是"请打个 1-10 分"

**`scoring/validate_judge.py` — 这一步最容易被跳过，但最重要**

验收：
- [ ] 手工标注 20 条样本的对错
- [ ] 用裁判跑这 20 条，**对比裁判和你的判断是否一致**
- [ ] 算出裁判的一致率。如果低于 80%，说明你的 rubric 或裁判 prompt 有问题，**先修裁判再评 Agent**
- [ ] 写下：一个不可靠的裁判，会让你做出什么错误决策？

**`trace_viewer.py`**

验收：
- [ ] 能读取 `03` 存的轨迹文件，打印成人能看的过程
- [ ] 失败的样本，能一眼看出**是在哪一步错的**
- [ ] 记录**过程指标**：平均步数、工具调用次数、有多少步是无效的

**`cost_report.py` — 成本分析**

验收：
- [ ] 统计每个样本的 token 和成本，找出最贵的 5 条，分析为什么贵
- [ ] 分析：输入 token 里，有多少是**重复的历史**？有多少是工具结果？
- [ ] **实验提示词缓存**：
  - [ ] 记住前提：DeepSeek 的缓存是**自动的、默认开的，没有开关**。
        所以你不能"开启缓存"，只能"让前缀变得可命中"
  - [ ] 把稳定内容（system prompt、工具定义）放前面，易变内容放后面
  - [ ] 跑 10 次，观察 `usage.prompt_cache_hit_tokens` 这个字段
  - [ ] **如果命中数是 0，找出是哪个"隐形杀手"在破坏缓存**（常见元凶：system prompt 里塞了当前时间、工具列表顺序不固定、JSON 没排序）。
        注意 DeepSeek 的要求比一般实现更严：前缀必须**完整匹配**才算一个独立单元，
        差一个字节整段就不算数
  - [ ] 算出缓存到底省了多少钱（提示：命中 $0.003 vs 未命中 $0.15，差 50 倍）
- [ ] 实验 `reasoning_effort`：从默认的 `high` 调低之后，通过率掉多少？成本降多少？
      **用数据决定该用哪档**。别忘了思考花的 token 算在 `completion_tokens` 里，
      可以从 `usage.completion_tokens_details.reasoning_tokens` 单独看

**`guardrails` 部分**

验收：
- [ ] 输入侧：拦截明显恶意的输入（比如"忽略你之前的所有指令"）
- [ ] 输出侧：校验输出格式，不符合就拦截
- [ ] 高危操作（删文件、发请求、花钱）**必须人工确认**才能执行 —— 接一下 `08` 里那个工具投毒实验的结论
- [ ] 记录：护栏拦掉了多少正常请求？（误杀率也是个指标）

## 刻意不用的东西

- **不用托管评估平台**（LangSmith 之类）打头阵。先用文件 + 脚本，理解"评估"到底是什么，再决定要不要上平台
- **不用模型自动生成评估集**。参考上面说的理由
- **不追求 100% 通过率**。你的评估集里本来就该有本来就该失败的难题

## 踩坑提醒

- **你会为了评估集而调优，这叫过拟合**。所以必须留 train / test 分割，test 别偷看
- **LLM 裁判有偏差**：它倾向于给长的、语气自信的答案打高分。这就是为什么要先验证裁判
- **缓存被破坏是静默的**：不会报错，只会悄悄变贵。所以必须盯着
  `usage.prompt_cache_hit_tokens` 看
- **成本要算"完成一个任务"的总成本**，不是"一次请求"的成本。便宜但需要重试三次的配置，其实更贵
- **护栏会误杀**。加了护栏之后要重跑评估集，确认通过率没掉

## 自测问题

1. 为什么"模型生成评估集 + 模型当裁判"是自欺欺人？
2. 你怎么知道你的 LLM 裁判是可靠的？
3. 你的 Agent 通过率从 70% 涨到 85%，你怎么确认不是过拟合了评估集？
4. 提示词缓存命中率是 0，你排查的第一步是什么？
5. 把 `effort` 从高降到低，通过率掉了 3%，成本降了 40%。你会怎么选？说说判断依据
6. 过程指标（步数、无效步数）能告诉你哪些"只看通过率"看不到的东西？
