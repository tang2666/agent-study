# 04 — 记忆

## 要搞懂什么

`03` 里你已经发现了一个问题：对话越长，`messages` 越大，每轮请求越贵，最后装不下。

这一层解决的就是这个。而且要把两个完全不同的问题分开：

- **短期记忆**：本次会话内的上下文。核心矛盾是「装不下」和「贵」
- **长期记忆**：跨会话持久化。核心矛盾是「什么时候写」和「写什么进去」

**这两件事经常被混为一谈，但它们的解法完全不一样。**

- **上下文管理的三种策略**，以及各自的代价：
  - **滑动窗口**：保留最近 N 轮。简单，但会丢早期信息
  - **摘要压缩**：把早期内容总结掉。省 token，但总结会丢细节，而且总结本身要花钱
  - **服务端压缩（compaction）**：API 层面的能力，自动在接近上限时压缩
- **上下文清理（context editing）**：把旧的工具结果、思考块**清掉**，和压缩不一样 —— 清理是不总结、直接删
- **长期记忆的写入策略**：什么值得记？谁来决定？记错了怎么改？
- 上面这两点在**缓存**上的后果（决定成本差异的关键，见 `10-eval`）

## 要写的代码

```
04-memory/
├── 01_naive.py         # 不做任何处理，观察它什么时候崩
├── 02_window.py        # 滑动窗口
├── 03_summarize.py     # 摘要压缩
├── 04_compaction.py    # 服务端压缩
├── 05_context_edit.py  # 上下文清理
└── 06_longterm.py      # 跨会话长期记忆
```

**`01_naive.py` — 先制造问题**

把 `03` 的 Agent 拿来，喂一个会跑很多轮的任务（比如让它连续查 30 个城市）。

验收：
- [ ] 记录每轮的输入 token 数和单轮成本，画出来（贴个表格就行）
- [ ] 观察成本怎么涨的 —— 不是线性，是**平方级**的（因为每轮都重发全部历史）
- [ ] 一直跑到装不下，看报什么错
- [ ] 写下来：这就是为什么需要这一层

**`02_window.py` — 滑动窗口**

验收：
- [ ] 只保留最近 N 轮（N 自己定，比如 10）
- [ ] 成本变平了，不再随轮数上涨
- [ ] **找一个它会失灵的案例**：早先告诉它的关键信息被挤掉了，导致答错
- [ ] 记录下这个失败案例，后面的方案要能解决它

**`03_summarize.py` — 摘要压缩**

验收：
- [ ] 上下文超过阈值时，把早期消息总结成一段文字
- [ ] 关键点：**总结是另一次 LLM 调用**，它的成本也要算进去
- [ ] 对比 `02`：那个失灵案例现在解决了吗？
- [ ] 找一个摘要压缩会失灵的新案例（提示：需要精确原文的场景，比如具体数字、代码）
- [ ] 打印"原始 token 数 / 压缩后 token 数 / 压缩调用花的 token 数"，算出净收益

**`04_compaction.py` — 服务端压缩**

用 API 提供的压缩能力，让服务端自动处理。

验收：
- [ ] 开启压缩后跑一个长对话，确认它能自动工作
- [ ] **关键坑**：每轮必须把**完整的 `response.content`** 追加回 `messages`，不能只取文本
      （只取文本字符串会丢掉压缩状态，然后你会看到它莫名其妙地"忘事"）
- [ ] 打印 `usage`，确认压缩确实减少了输入 token
- [ ] 能说出：服务端压缩和你自己在 `03` 里写的压缩，各有什么取舍？

**`05_context_edit.py` — 上下文清理**

长任务里，工具结果往往占了绝大部分 token。把旧的清掉。

验收：
- [ ] 配置成自动清理旧的工具结果
- [ ] 对比清理前后：token 数降了多少？任务还能完成吗？
- [ ] 能说清"清理"和"压缩"的区别 —— 一个是删，一个是总结。什么时候该删而不是总结？
- [ ] 想一想：如果被清掉的结果后面又被需要，会怎样？

**`06_longterm.py` — 长期记忆**

实现跨会话记忆：程序重启后还记得用户。

验收：
- [ ] 存到本地（SQLite 或 JSON 都行），不要只用内存
- [ ] 设计**写入策略** —— 这是这一层的核心问题：
  - 是每轮都存？还是让模型判断"这条值得记"？
  - 冲突怎么办（用户先说喜欢咖啡，后来说喜欢茶）？
  - 谁来决定"忘掉"？
- [ ] 实现**召回**：新会话开始时，怎么决定哪些记忆该加载进上下文？全load进去会怎样？
- [ ] 至少跑通这个场景：会话 A 告诉它一件事 → 退出程序 → 会话 B 里它还记得

## 刻意不用的东西

- **不用向量数据库做长期记忆**。先用最简单的键值存储或 SQLite，把"写什么/什么时候读"想清楚。向量检索解决的是"记忆太多找不过来"，不是"该不该记"——后者才是真问题。`05-rag` 里再上向量
- **不用任何记忆框架**。这一层就是要把策略自己想一遍

## 踩坑提醒

- 成本是**平方级**增长的，不是线性。第 50 轮的成本和第 1 轮不是一个量级
- **摘要会丢信息，而且丢得静默无声**。你不会收到报错，只会发现 Agent 突然变笨。测试时要专门造"需要早期精确信息"的案例
- **缓存会被你的压缩策略破坏**。上下文一变，缓存前缀就失效了。所以"压缩省了 token"和"压缩破坏了缓存"可能互相抵消 —— 这个账要一起算。
  **在 DeepSeek 上这个账特别重**：缓存命中 $0.003 vs 未命中 $0.15，差 50 倍。
  而且它的前缀必须**完整匹配**才算一个独立单元 —— 你在历史中间插一句摘要，
  从那一句往后的全部前缀都废了。所以"压缩"到底省钱还是烧钱，
  得看你是**改动尾部**还是**改动中间/头部**
- 长期记忆**写入容易，删除难**。设计时就要想好怎么纠正错误记忆，否则错了会一直错下去
- 不是所有模型都支持服务端压缩，用之前确认一下。
  （DeepSeek 的 Chat Completion API 不支持在对话中间插入工具调用，
  只支持中间插入 system 消息 —— 设计压缩策略时这条约束会咬你）

## 自测问题

1. 滑动窗口、摘要、服务端压缩，各自的失败模式是什么？
2. 为什么"清理旧工具结果"和"摘要早期对话"是两件事？
3. 长期记忆里，"什么时候写" 和 "写什么" 哪个更难？为什么？
4. 如果缓存是默认自动生效的，那你压缩上下文之后，成本到底是升是降？取决于什么？
5. 用户说"忘记我之前说的"，你的实现支持吗？如果不支持，回去补
