# 05 — 检索增强生成（RAG）

## 要搞懂什么

`04` 讲的是"记住对话"，RAG 讲的是"**接入外部知识**"。两者都是在往上下文里塞东西，但来源和检索方式完全不同。

核心链条：**切分 → 嵌入 → 存储 → 检索 → 重排 → 生成**

- **切分（chunking）**：切多大？按什么切？为什么这是 RAG 里最影响效果的一步
- **嵌入（embedding）**：把文本变成向量。注意嵌入模型要单独选一个，不要拿对话模型当嵌入用
- **向量检索的局限**：为什么"语义相似"不等于"能回答我的问题"
  - 关键词匹配 vs 语义匹配，各自的盲区
  - **混合检索**：两者结合
- **重排（rerank）**：先粗筛再多精排，为什么这样更划算
- **引用（citation）**：让答案能追溯到原文
- **RAG 的评估**：检索质量 vs 生成质量，得分开评
- **Agentic RAG**：让模型自己决定"要不要检索、检索什么、够不够、再检索一次"。这才是 RAG 和 Agent 的交汇点

## 要写的代码

```
05-rag/
├── corpus/                 # 自己准备 10-20 个文档（md 或 txt，中文）
├── 01_chunk.py             # 切分
├── 02_embed.py             # 嵌入 + 存储
├── 03_retrieve.py          # 相似度检索
├── 04_hybrid_rerank.py     # 混合检索 + 重排
├── 05_rag_pipeline.py      # 完整问答
├── 06_agentic_rag.py       # 带检索工具的 Agent
└── eval/                   # 评估集
```

> 语料自己造。建议用你熟悉领域的文档（比如某个库的中文文档、几篇技术博客），至少 10 篇。这样你**知道正确答案是什么**，才能判断检索对不对。

**`01_chunk.py`**

验收：
- [ ] 实现至少两种切分策略：固定长度、按语义结构（标题/段落）
- [ ] 打印每种策略切出来的块数、平均长度、最长最短
- [ ] **故意切坏一次**：让某个关键句子被从中间切开，看后面检索会怎样
- [ ] 记下结论：块大小的取舍是什么？

**`02_embed.py`**

选一个嵌入模型（本地的或第三方的都行），把块转成向量存下来。

验收：
- [ ] 存到本地能持久化（SQLite + 向量、或者 numpy 存文件都行）
- [ ] 记录每个块的原文、来源文档、位置
- [ ] 能说出：为什么必须存来源？不存会怎样？

**`03_retrieve.py`**

验收：
- [ ] 给定问题，返回 top-k 最相似的块
- [ ] 准备 5 个问题，其中**至少 2 个是关键词能答对的、2 个是必须语义理解才能答对的**
- [ ] 观察：纯向量检索在关键词类问题上是不是会翻车？举出具体案例
- [ ] 打印相似度分数，看看分数和"是否真的相关"是否一致

**`04_hybrid_rerank.py`**

验收：
- [ ] 实现混合检索：关键词（BM25 或者简单的词频） + 向量，两路结果融合
- [ ] 加一层重排：先取 top-20，再用模型/重排器精排到 top-5
- [ ] 对比 `03` 的失败案例，现在解决了吗？
- [ ] 打印耗时：重排让延迟增加了多少？值不值？

**`05_rag_pipeline.py`**

完整流程：问题 → 检索 → 拼进上下文 → 生成答案。

验收：
- [ ] 答案必须**带引用**，标出是哪篇文档的哪一段
- [ ] 检索不到相关内容时，明确回答"文档里没有"，**不要瞎编**
- [ ] 自己写 15 个问答对做评估集（问题 + 标准答案 + 应该命中的文档）
- [ ] 算两个指标：**检索命中率**（该命中的文档有没有被检索到）、**答案准确率**
- [ ] **关键**：把两个指标分开看。答错了，是"没检索到"还是"检索到了但没答对"？这两种失败原因的修法完全不同

**`06_agentic_rag.py`**

把检索包装成一个工具，接回你 `03` 写的 Agent。

验收：
- [ ] Agent 自己决定要不要检索、检索什么
- [ ] 支持**多轮检索**：第一次没找到，能换个说法再找
- [ ] 造一个必须检索两次才能回答的问题（第一次的信息不够）
- [ ] 对比 `05` 的固定流程：什么时候 Agentic 更好？什么时候纯属浪费？

## 刻意不用的东西

- **不用 `langchain` 的检索器 / `llama_index`**。整个流程手写一遍。这两个库把 RAG 包得很好，但也很容易让人以为"调通了 = 懂了"
- **不用托管向量数据库**（Pinecone 之类）。本地 SQLite / numpy 够了，你要理解的是检索原理不是运维
- **不要一上来就上 RAG**。先问自己：把文档直接塞进上下文行不行？（100 页以内、或者只问一次的场景，直接塞往往更好）

## 踩坑提醒

- **切分是最大的效果杀手**，比换模型影响大得多。关键句子被切两半，检索再准也白搭
- **嵌入模型和生成模型是两回事**，要分别选、分别评
- **相似度高 ≠ 有用**。一个块可能和问题语义很像但完全不包含答案。这就是为什么需要重排
- **top-k 不是越大越好**。k 太大会把噪声塞进上下文，反而降低准确率，还更贵
- 评估集要**自己写**。用模型生成评估集，然后发现模型"考得不错"，这是自欺欺人

2. 重排为什么"先粗筛再多精排"更划算，而不是直接用大模型精排全部？
3. 你的 RAG 答错了一个问题。你怎么判断是检索的锅还是生成的锅？
4. Agentic RAG 比固定流程贵，什么情况下它值得？
5. 上下文窗口有 1M token，那是不是可以直接把整个知识库塞进去，不要 RAG 了？说说你的取舍
