# 06 — Agent 设计模式

## 要搞懂什么

`03` 你实现的是 **ReAct** 模式的循环。但 ReAct 不是唯一答案，而且它在某些任务上表现很差。

这一层要做的核心事情是：**用同一个任务，实现三种模式，公平对比。**

- **ReAct**：边想边做，走一步看一步。适合探索性任务、路径不确定的任务
- **Plan-and-Execute**：先出完整计划，再逐步执行。适合步骤明确的复杂任务
  - 关键矛盾：计划是**一次性定死**，还是**执行中可以改**？
  - 计划错了怎么办？重新规划的成本有多高？
- **Reflection / Reflexion**：做完之后自己检查、自我批评、然后改
  - 关键问题：**批评自己的模型和干活的模型是同一个**，它凭什么能发现自己错了？
  - 什么时候反思有用？什么时候只是白花钱？
- **什么时候不该用 Agent**。这是最容易被忽略的模式 —— 很多需求其实一个固定的工作流就够了，不需要 Agent
  - 判断标准：任务能完全预先描述清楚吗？需要模型自己决定下一步吗？

## 要写的代码

```
06-patterns/
├── common/                 # 共用的工具、模型调用、日志（复用 03 的）
├── bench.py                # 统一的对比跑分脚本
├── task_a/                 # 任务 A：探索型（步骤不确定）
├── task_b/                 # 任务 B：流程型（步骤明确）
├── pattern_react.py
├── pattern_plan_execute.py
├── pattern_reflection.py
└── pattern_workflow.py     # 对照组：纯代码固定流程，不用模型决策
├── results.md              # 对比结论
```

**两个任务，要设计得能区分出模式的差异**

- **任务 A（探索型）**：比如"在给定的 20 个文本文件里找出所有提到某个概念的地方，并总结它们的关系"。你事先不知道会找到什么，也不知道要找几轮
- **任务 B（流程型）**：比如"把这个 CSV 清洗成指定格式，校验字段，生成报告"。步骤完全确定，只是每步需要模型理解

**`pattern_react.py`**

直接复用 `03` 的循环，接上这两个任务。

**`pattern_plan_execute.py`**

验收：
- [ ] 第一阶段：模型输出一个**结构化的**计划（步骤列表，可解析）
- [ ] 第二阶段：逐步执行计划
- [ ] 执行中发现某步失败 → 实现**重新规划**，而不是直接崩
- [ ] 打印计划，看清模型规划的质量。**找一个它规划得很烂的案例**

**`pattern_reflection.py`**

验收：
- [ ] 模型给出答案后，再来一轮："检查上面的答案，找出错误"
- [ ] 有错就改，改完可以再检查（设个上限，比如 2 轮）
- [ ] 关键实验：**反思真的提升了结果吗？** 记录"反思前 / 反思后"的准确率
- [ ] 如果提升不明显，思考：是不是因为批评者和执行者是同一个模型，它看不出自己的错？（这叫"自评偏差"，是个真问题）

**`pattern_workflow.py` — 对照组**

不准用 Agent 循环。用纯代码把任务 B 的流程写死：读文件 → 调模型做清洗 → 校验 → 调模型写报告。

验收：
- [ ] 能跑完任务 B
- [ ] 对比：它和 Plan-and-Execute 版的准确率、成本、延迟各是多少？
- [ ] 写下结论 —— 大概率你会发现：**在流程确定的任务上，写死的工作流又快又便宜又准**

**`bench.py` + `results.md`**

验收：
- [ ] 一张表，行是模式（含 workflow 对照组），列是任务 A / 任务 B
- [ ] 每个格子填：成功率、总成本、平均延迟、总步数
- [ ] **每个任务跑至少 3 次**，填平均值 —— 单次结果没有意义，模型有随机性
- [ ] `results.md` 写结论：哪个模式在哪个任务上赢？为什么？和你的预期一致吗？

## 刻意不用的东西

- **不用框架的 pattern 封装**。LangGraph 里有现成的 ReAct / Reflection 模板，这一层不许用
- **不用多 Agent**。那是 `07` 的事。这一层所有模式都是**单 Agent**
- **不做泛泛的性能测试**。必须绑定具体任务，否则得出的结论没法用

## 踩坑提醒

- **反思模式很容易变成"表演"**：模型说"我检查了一遍，没有问题"，但其实有问题。要有外部校验手段（比如任务有标准答案就拿来对）
- **Plan-and-Execute 的计划会过期**：执行到第 3 步发现第 1 步的假设错了，这时候硬着头皮执行完是最差的选择
- **公平对比很重要**：同一个模型、同一套工具、同一个任务，只换模式。否则你比较的是别的东西
- **单次跑分不可信**。模型有随机性，任务又复杂，跑 1 次得出的"A 比 B 好"可能是噪声

## 自测问题

1. ReAct 和 Plan-and-Execute 各自会在什么任务上翻车？
2. 反思为什么可能无效？有什么办法让它更有效？
3. 任务 B 上，你的 workflow 版本和 Agent 版本谁赢了？这个结果说明什么？
4. 拿到一个新需求，你怎么判断该用 Agent 还是写死工作流？说一套你自己的判断标准
5. 如果 ReAct 和 Plan-and-Execute 在任务 A 上打平，成本也差不多，你会选哪个？为什么？
