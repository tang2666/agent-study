# 07 — 多 Agent 协作

## 要搞懂什么

先记住一句话：**多 Agent 不是升级，是权衡。** 它解决的是一类特定问题，同时带来一堆新问题。

- **它真正解决的问题**：
  - **上下文隔离** —— 一个 Agent 读 50 个文件会把上下文撑爆。拆开成多个 Agent，每个只看自己那部分
  - **职责边界** —— 一个 Agent 又要写代码又要审查代码，两套规则会打架。拆开后各自的提示词更干净
  - **并行** —— 独立子任务可以同时跑
- **它带来的新问题**（这些往往比它解决的问题更麻烦）：
  - **成本爆炸**：每个 Agent 都是一次完整的模型调用，还有协调开销
  - **信息损耗**：主 Agent 交给子 Agent 的任务描述，本身就是一次"翻译"，会丢信息
  - **错误传播**：子 Agent 给了一个错的结论，主 Agent 基于它继续做，最后错得很离谱还查不出来
  - **调试地狱**：出错了，你得先搞清楚是哪个 Agent 的锅
- **常见架构**：
  - **Manager-Worker（主管-工人）**：一个主管拆任务、分派、汇总。最常用
  - **Pipeline**：A 的输出给 B，B 给 C。简单，但 A 错了会一路错下去
  - **辩论 / 投票**：多个 Agent 独立给答案，再综合。成本高，但能减少单点偏差
- **子 Agent 的上下文从哪来**：是继承父 Agent 的全部历史，还是从零开始只给它任务描述？

  **这个选择决定了多 Agent 到底能不能省 token。** 如果子 Agent 继承了全部历史，那你只是把一次大调用拆成了多次大调用 —— 更贵，没有任何收益

## 要写的代码

```
07-multi-agent/
├── common/                 # 复用前面的工具和模型封装
├── orchestrator.py         # 主管逻辑：拆任务、分派、汇总
├── worker.py               # 子 Agent：独立上下文、自己的工具子集
├── 01_manager_worker.py
├── 02_pipeline.py
├── 03_debate.py
├── compare.py              # 和单 Agent 对比
└── results.md
```

**选一个任务**：建议用"研究类"任务，比如"分析这 10 篇文档，回答一个需要综合的问题"。这类任务天然可以拆分。

**`01_manager_worker.py`**

验收：
- [ ] 主管 Agent 拿到大任务，拆成子任务（结构化输出，可解析）
- [ ] 每个子任务交给一个**独立的** Worker，Worker 有自己的 `messages` 列表，**不继承主管的历史**
- [ ] Worker 只拿到：任务描述 + 它能用的工具 + 它的上下文范围
- [ ] 主管汇总各 Worker 的产出，给出最终答案
- [ ] 打印每个 Worker 的输入 token 数，验证它们确实是隔离的

**`02_pipeline.py`**

验收：
- [ ] A → B → C 的串行流程
- [ ] 故意让 B 拿到一个 A 给错的信息，观察错误一路传下去、最后错成什么样
- [ ] 思考：有没有办法在上游就检出这种错误？

**`03_debate.py`**

验收：
- [ ] 3 个 Agent 独立回答同一个问题（**互不可见**，这点很重要）
- [ ] 第 4 个 Agent 看三份答案，综合出最终结论
- [ ] 造一个问题，让 3 个 Agent 大概率会给出不同答案，观察综合的效果
- [ ] 算成本：辩论版本是单 Agent 的几倍？值得吗？

**`compare.py` + `results.md`**

和 `03` 里的单 Agent 版本公平对比同一个任务。

验收：
- [ ] 表格：单 Agent / Manager-Worker / Pipeline / Debate，比较成功率、总成本、总 token、延迟、**出错时的定位难度**
- [ ] 每个配置至少跑 3 次
- [ ] `results.md` 必须回答一个问题：**多 Agent 到底赢在哪？如果没赢，是为什么？**
- [ ] 诚实面对结论。如果单 Agent 更好，就写"单 Agent 更好"

## 刻意不用的东西

- **不用 `crewai` / `autogen` / LangGraph 的多 Agent 封装**。自己写协调逻辑
- **不让子 Agent 继承父 Agent 的完整上下文**。这是这一层的核心实验约束 —— 你要亲自验证"上下文隔离"到底有没有带来收益
- **不做没有对照组的实验**。"多 Agent 效果不错"这句话在没有单 Agent 基线时毫无意义

## 踩坑提醒

- **协调开销会吃掉所有收益**。主管拆任务、汇总结果都是额外的模型调用，算总账经常是亏的
- **信息在传递中损耗**：主管说"去查一下那个东西"，子 Agent 根本不知道"那个东西"指什么。任务描述必须自包含
- **别让子 Agent 无限递归**：子 Agent 又拆子 Agent，很快就是几十个调用。层级限制在 2 层
- **汇总者也可能是瓶颈**：10 个 Worker 各返回 2000 字，主管的上下文一样会被撑爆
- **调试成本被严重低估**：出错了要翻 N 份轨迹。所以 `03` 里的轨迹记录在这一层更重要

## 自测问题

1. 多 Agent 真正解决的核心问题是什么？用一句话说。
2. 什么情况下多 Agent 一定亏？（提示：子任务之间强依赖的时候）
3. 子 Agent 该不该看到父 Agent 的历史？各自的代价是什么？
4. 你的实验结果里，多 Agent 赢了吗？如果输了，你觉得是任务选得不合适，还是多 Agent 本身就不适合这个场景？
5. 一个子 Agent 返回了错误的结论，主 Agent 据此做完了整个任务。你怎么在设计上减少这种风险？
