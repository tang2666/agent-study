# 01 — 提示词 & 结构化输出

## 要搞懂什么

核心目标只有一个：**让 LLM 的输出变成程序能可靠使用的数据**。

这是从"聊天玩具"到"能写进程序里的组件"的关键一步。做不好这个，后面 Agent 里模型返回的东西永远是"看起来像 JSON 的字符串"，只能靠正则去抠，一改就崩。

- **system prompt 的作用**：它是"角色和规则"，不是"内容"。跟用户消息的职责划分
- **提示词的作用范围**：什么该写进 prompt，什么该写进代码。判断标准是"这事需要用自然语言理解吗"
- **CoT（思维链）**：让模型先推理再给结论，为什么有效。**注意 DeepSeek 有原生思考模式**（默认开着），所以在这里你要分清"手动在 prompt 里求 CoT"和"模型自己就在想"的区别
- **结构化输出**：`response_format={"type": "json_object"}` 强制模型输出合法 JSON
- **`strict: true`**：工具定义上的严格模式（Beta，需换 `/beta` 端点），保证参数一定符合 schema
- **失败模式**：模型不遵守格式时，你的代码应该怎么办

## 要写的代码

```
01-prompting/
├── 01_system_prompt.py     # system / user 职责划分
├── 02_json_output.py       # 结构化输出
├── 03_extract.py           # 真实提取任务
├── 04_cot.py               # 思维链
└── 05_robust.py            # 输出校验与重试
```

**`01_system_prompt.py`**

同一个问题，写两个不同 system prompt，对比输出。

验收：
- [ ] 一个写得好的、一个写得很差的，能明确说出差在哪
- [ ] 试验：把重要规则从 system 挪到第一条 user 消息里，输出有区别吗？为什么？
- [ ] 能说出 system prompt 和 user 消息在**缓存**上的区别（不知道就先记下问题，`10-eval`/成本那部分会回来讲）

**`02_json_output.py`**

让模型输出一个固定 schema 的对象，比如：

```json
{"name": "张三", "age": 30, "skills": ["python", "sql"]}
```

验收：
- [ ] 用 `response_format={"type": "json_object"}` 强制格式，而不是只在提示词里写"请返回 JSON"
- [ ] **提示词里必须出现 "json" 这个词**，并且给一个期望格式的**例子**。
      官方明确要求这两点，不给的话模型可能一直输出空白直到撞上限
- [ ] 拿到的 `message.content` 是**字符串**，**要自己 `json.loads()`**
      （注意：这跟 Claude 的结构化输出不一样，Claude 那边能直接给你解析好的对象。
      DeepSeek 只保证"是合法 JSON 字符串"）
- [ ] 故意把 schema 写复杂一点（嵌套对象 + 数组 + 枚举），确认依然稳定
- [ ] **撞一次那个已知问题**：官方承认 JSON 模式下**偶尔会返回空的 content**。
      跑个二三十次看你能不能撞上，然后想好你的代码该怎么办
      （提示：这就是 `05_robust.py` 要处理的事）

**`03_extract.py`**

从一段非结构化的中文文本（自己编一段简历/邮件/会议记录）里抽取结构化信息。

验收：
- [ ] 至少 5 个字段，含一个嵌套结构
- [ ] 输入 10 段不同文本，**全部**成功解析，没有一次需要人工修
- [ ] 对"文本里没有这个信息"的情况有明确处理（返回 null 还是猜一个？schema 怎么设计？）

**`04_cot.py`**

这一节要分清**两种 CoT**，这是个容易糊在一起的概念：

- **A：手动 CoT** —— 在 prompt 里要求"先分步推理再给结论"，推理过程写在 `content` 里
- **B：直接问答案**，不要求推理
- **C：原生思考模式** —— DeepSeek 默认就开着，推理过程在 `reasoning_content` 里，
  和 `content` **天然分开**

自己选一个需要推理的问题（简单逻辑题/数学题）。

验收：
- [ ] 跑 A vs B，能观察到 A 更准（如果一样准，换个更难的问题）
- [ ] 跑 C，**对比"开思考"和"关思考"**（关掉的方法见 `00-hello-llm` 约定 2）
- [ ] **关键对比**：A 和 C 的推理过程分别在哪个字段？
      这说明"原生思考模式"比"手动 CoT"多解决了什么问题？
- [ ] 思考：如果下游程序只需要结论，A 和 C 各自要怎么处理才能拿到干净结果？
      哪个更省事？为什么？

**`05_robust.py`**

假设模型**偶尔**会返回不合格式的东西（可以人为在 prompt 里埋雷，或直接从历史版本里复制一个真实失败案例）。

验收：
- [ ] 有校验：解析后检查字段是否齐全、类型对不对
- [ ] 校验失败时**重试**，并且把错误信息回传给模型让它自己修
- [ ] 重试上限 2 次，超过就抛异常，不要无限重试
- [ ] 记录重试率。如果重试率很高，说明提示词或 schema 有问题，不是重试能解决的

## 刻意不用的东西

- **不用框架的 output parser**。自己写校验和重试，理解里面在做什么
- **不靠"请返回 JSON"这种嘴说**。有 `response_format` 这个约束机制就用它
- **不用 prefill 技巧**。DeepSeek 确实有个 Chat Prefix Completion，但它是 **Beta 功能，必须把 `base_url` 换成 `https://api.deepseek.com/beta`，并且那个 assistant 消息要设 `prefix: true`**。
      不是"传了就行"，也不是老教程里那种写法。这一章用 `response_format` 就够，别绕这条远路

## 踩坑提醒

- **`json.loads()` 省不掉**。`response_format` 保证的是"输出是合法 JSON 字符串"，
      不是"已经帮你解析成 dict 了"。你拿到的仍然是 `message.content` 这个字符串
- **JSON 模式下 `max_tokens` 别设太小**。官方专门提醒：设得不合理会让 JSON 字符串
      从中间被截断，`finish_reason` 变成 `length`，那串东西直接没法解析
- **思考模式下 `content` 可能为空**（跟上面那个已知问题是两码事，这个是设计如此）。
      校验的时候要把"空"和"格式错"分开处理，别混成一个错误
- **`strict: true` 只作用于工具定义的 schema**，不是给 `response_format` 用的，
      而且要换 `/beta` 端点。别把它当成"结构化输出的开关"

## 自测问题

1. 为什么光在提示词里写"请返回 JSON"不可靠？`response_format` 又可靠在哪、不可靠在哪？
2. `strict: true` 和 `response_format` 分别管什么？为什么 `strict: true` 不能当"结构化输出的开关"用？
3. CoT 让输出变长、变贵，什么时候值得？什么时候是浪费？原生思考模式和手动 CoT 在成本上有什么区别？
4. 校验失败时重试，为什么要把错误信息告诉模型，而不是原样重发一次？
